# OpenClaw + 学习网站插件方案可行性评估

## 结论

这个方向在技术上是 **部分可行** 的。

可行的是：

- 复用 `xiaohongshu` 的整体模式，做成 `Chrome 扩展 + 本地 bridge server + Python CLI + SKILL.md`。
- 在用户自己完成登录后，由扩展读取当前页面状态。
- 自动进入课程页、读取课程列表、读取章节/视频/任务点状态、汇总学习进度。
- 对普通 DOM 交互做自动化，例如点击章节、切换标签、读取文本、滚动页面。

不应直接按“自动刷课 / 伪造学习进度”作为目标推进。原因不是前端点按钮本身，而是学习平台的视频完成、任务点完成、考试/作业提交，通常都依赖服务端校验、心跳上报、行为检测、验证码或风控策略。即使前端能播放视频，也不等于平台会记为有效学习。

## 为什么说它和小红书 skill 在架构上相似

`xiaohongshu` skill 的关键不是“小红书”本身，而是这条通用链路：

1. Chrome 扩展注入目标站点页面。
2. 扩展通过 WebSocket 连接本地 `bridge_server.py`。
3. Python CLI 把“打开页面 / 查元素 / 点击 / 读文本 / 执行 JS”之类命令发给 bridge。
4. `SKILL.md` 只负责把自然语言路由到 CLI。

这套模式对“登录后由用户浏览器代执行”的网站都能复用。你的学习网站如果主要靠浏览器页面交互完成操作，这个模式是合适的。

## 从你给的信息看，当前网站的已知特征

基于你提供的 HTML 和现成脚本，已经能确认几件事：

- 登录入口看起来是超星系页面，存在账号登录和扫码登录两种模式。
- 登录页包含滑块验证码模块，这意味着“自动登录”不是稳定目标。
- 页面里出现了 iframe，后续课程页大概率也会有多层 iframe 或嵌套播放器。
- 现成“刷课脚本”是油猴注入式方案，说明前端页面层面的自动化空间确实存在。
- 但油猴脚本支持“自动答题/自动考试/自动跳任务点”不代表它稳定，也不代表服务端一定认可最终进度。

## 可行范围

建议把能力拆成两层：

### A. 合规、稳定、可维护的能力

- 检查是否已登录。
- 读取用户昵称、课程列表、章节树、视频列表。
- 读取每门课的完成度、未完成章节、任务点状态。
- 打开指定课程并导航到指定章节。
- 采集页面结构和请求特征，辅助后续人工分析。

这部分最适合先做，因为它主要是“观测”和“导航”，稳定性高，也更接近 `xiaohongshu` 现有桥接模型。

### B. 高风险、不稳定的能力

- 自动连续播放视频直到平台记为完成。
- 自动跳过限制逻辑或任务点校验。
- 自动过验证码。
- 自动考试、自动作业提交、伪造心跳或伪造学习时长。

这部分通常会碰到平台规则、风控、接口签名、播放器上报、课程 iframe 隔离等问题。技术难度不是完全做不到，而是维护成本高、失效率高，而且容易演变成绕过平台限制。

## 主要技术阻塞点

### 1. 登录不是主要难点，登录后的状态保持才是

扫码登录可以让用户手动完成，扩展复用浏览器现有登录态即可。

真正的问题是：

- 登录态可能分散在多个二级域名 cookie 中。
- 课程页可能从主站跳到别的域名。
- 视频页、考试页、章节页可能不是同一个 origin。

这要求扩展的 `host_permissions` 不能只写一个域名，往往要覆盖：

- `*.chaoxing.com`
- 某些学校域名
- 课程/播放器实际落地的域名

### 2. iframe 很可能是核心难点

学习平台经常把课程内容、播放器、答题页放在 iframe 里。

这会带来两个问题：

- content script 默认不一定进入所有 frame。
- 选择器和点击逻辑要区分“主页面”与“子 frame 页面”。

如果后续目标只是读取课程目录和进度，问题可控。
如果目标是操作播放器或任务点，iframe 基本是必须单独处理的。

### 3. “播放了”不等于“进度记上了”

很多学习站的有效进度依赖：

- 定时心跳请求
- 当前播放位置上报
- 页面停留时长
- 页面可见性
- 防拖动/防倍速/防静音/防后台
- 任务点切换顺序

所以插件能点开视频，只能证明“前端可操作”。
要确认“能自动获取有效学习进度”，必须实际抓一次完整学习流程，观察：

- 播放时发了哪些请求
- 哪个请求会更新完成度
- 切到下一节的触发条件是什么

### 4. 验证码和风控会让“无人值守”能力大打折扣

你给的 HTML 里已经有滑块验证码。
这意味着至少在登录、异常访问、频繁操作时，平台可能要求人工介入。

所以更现实的定位是：

- 用户手动登录
- OpenClaw 读取状态、导航页面、辅助操作

而不是：

- 从零开始全自动无人值守完成整套学习

## 与油猴脚本相比，OpenClaw skill 的优劣

### 优势

- 有清晰的“扩展 / bridge / CLI / skill”分层。
- 更适合做结构化命令，例如 `check-login`、`list-courses`、`get-progress`。
- 可以把页面读取结果以 JSON 返回给 OpenClaw。
- 更容易逐步演进成稳定工具，而不是一大段难维护的单文件脚本。

### 劣势

- 初期开发量比直接改油猴脚本更大。
- 如果目标是复杂页面劫持、接口拦截、播放器 hook，油猴脚本原地注入有时更直接。
- 涉及多 iframe、多域名、复杂请求签名时，bridge 模式也不能自动降低难度。

## 最合理的实施路线

建议分三阶段，不要一开始就追求“刷课”。

### 阶段 1：先做只读能力

目标：

- `check-login`
- `list-courses`
- `get-course-detail`
- `get-progress`

验收标准：

- 用户手动登录后，OpenClaw 能稳定拿到课程和进度数据。

### 阶段 2：再做页面导航和轻交互

目标：

- `open-course`
- `open-chapter`
- `open-next-unfinished`

验收标准：

- OpenClaw 能把浏览器带到正确课程/章节页面。

### 阶段 3：只在明确合规场景下做“播放辅助”

目标：

- 仅做页面内播放器控制和状态读取，比如播放、暂停、当前时长、是否结束。

不建议把目标定义成：

- 伪造学习记录
- 绕过验证码
- 绕过任务点/考试限制

## 最终评估

如果你的目标是：

- “像小红书 skill 一样，让 OpenClaw 识别登录状态、读取课程和进度、打开课程、辅助页面操作”

那么可行性是 **高** 的。

如果你的目标是：

- “稳定无人值守自动刷完课，并确保平台百分之百记上学习进度”

那么可行性只能算 **中低**，而且主要障碍不在插件框架，而在平台的服务端校验、iframe、风控和实际业务规则。

## 推荐下一步

最值得先验证的不是“自动刷”，而是下面 3 件事：

1. 用一个最小 Chrome 扩展，先确认能在课程页读到课程名称、章节列表、进度文本。
2. 确认课程页是否存在多层 iframe，以及真正承载播放器/任务点的 frame URL。
3. 用浏览器开发者工具观察“开始播放一个视频”到“章节完成”之间的网络请求差异。

这 3 步如果打通，后面能不能继续做，就不再靠猜。

## 当前实测进展

截至 2026-05-03，`xuexitong` 原型已经在真实页面上打通了以下链路：

- Chrome 扩展已能连接本地 bridge server。
- Python CLI 已能读取当前激活标签页 URL、页面类型和基础 DOM。
- 课程外壳页可读取 `#frame_content` 内课程列表。
- 课程详情页可读取 `courseId`、`clazzId`、`cpi` 以及章节 iframe 地址。
- 章节任务页 `studentcourse` 已能稳定读取：
  - `courseId`
  - `clazzId`
  - 总进度文本，例如 `已完成任务点: 0/98`
  - 章节树是否存在
  - 搜索框是否存在
  - 章节单元列表
  - 子章节列表
  - 每个子章节的标题、序号、待完成任务点

当前在“中华民族精神”页面上的实测结果：

- 页面类型：`chapter_task`
- `courseId`：`260762408`
- `clazzId`：`141988491`
- 总进度：`0/98`
- 一级单元数：`11`
- 子章节数：`51`
- 已可解析出前若干章节，例如：
  - `1.1 民族、民族文化`
  - `1.2 何谓民族精神`
  - `1.3 中华民族精神面临的全球化挑战`
  - `1.4 中华民族精神与现代化`

这说明当前问题已经不是“能不能接入 OpenClaw”，而是“如何继续把章节点击、任务卡识别、播放器区域识别补齐”。

## 当前主链路验证结果

当前已在真实页面中验证通过的跳转链路如下：

1. 空间课程外壳页
2. 章节目录页 `studentcourse`
3. 学习页 `studentstudy`
4. 任务卡页 `mooc-ans/knowledge/cards`
5. 视频附件页 `ananas/modules/video/index.html`

这条链路已经说明：

- 章节项点击不是黑盒，DOM 中存在稳定的 `onclick="toOld(courseId, chapterId, clazzId, ...)"`。
- 章节目录页可以直接按 `chapterId` 打开指定章节。
- 学习页可以稳定读取 `courseId`、`clazzId`、`chapterId`、`studyStateRaw`、`card iframe src`。
- 任务卡页可以识别出视频附件 iframe，并拿到其 `data` 属性中的业务参数。
- 视频附件页已经能探测到播放器相关全局对象，例如：
  - `ananas`
  - `videojs`
  - `loadVideo`
  - `playVideo`
  - `showMoocPlayer`

## 目前还没闭环的部分

当前尚未正式实现的部分主要有：

- 自动回到上一层页面的导航命令
- 直接控制播放器开始播放
- 识别“当前任务点是否真正完成”
- 自动跳到下一任务点或下一章节
- 作业/测验页的结构化识别与提交流程

## 下一阶段最优先事项

后续最值得继续补的是两块：

1. 基于任务卡页中的视频附件元数据，补一个“视频任务探测 / 播放器状态探测”命令。
2. 识别播放器完成状态与章节任务完成状态之间的关联，确认平台到底依赖哪些前端/服务端信号。
